    API 参考

    Discord 的 API 基于两个核心层，一个是用于通用操作的 HTTPS/REST API，另一个是用于发送和订阅实时事件的持久性安全 WebSocket 连接。Discord API 最常见的用例是，通过 OAuth2 API 提供服务或访问平台。

    基础 URL
    https://discord.com/api

    API 版本控制

    一些 API 和网关版本现已无法运行，为方便查阅，在下表中标记为已停用。尝试使用这些版本将会失败并返回 400 Bad Request。

    Discord 暴露了我们 API 的不同版本。您应该通过将其包含在请求路径中来指定要使用的版本，例如 https://discord.com/api/v{version_number}

    从路由中省略版本号将把请求路由到当前默认版本（如下所示）

    身份验证

    通过 Discord API 进行身份验证可以通过两种方式完成：

    1. 使用您应用程序设置中“Bot”页面上的机器人令牌。有关机器人的更多信息，请参阅机器人与用户账户

    2. 使用通过 OAuth2 API 获得的 OAuth2 持有者令牌

    对于所有身份验证类型，身份验证都是通过 Authorization HTTP 头以 Authorization: TOKEN_TYPE TOKEN 的格式执行的

    持有者令牌授权头的示例

    加密

    Discord API 中的所有 HTTP 层服务和协议（例如 HTTP、WebSocket）都使用 TLS 1.2。

    雪花ID

    Discord 使用 Twitter 的雪花ID格式作为唯一标识符（ID）。

    这些 ID 在整个 Discord 中保证是唯一的，除了在某些子对象共享其父对象 ID 的特殊情况下。由于雪花 ID 的大小最大为 64 位（例如 uint64），因此在 HTTP API 中它们总是以字符串形式返回，以防止某些语言中出现整数溢出。有关网关编码的更多信息，请参阅网关 ETF/JSON。

    分页中的雪花ID

    我们通常在许多 API 路由中使用雪花 ID 进行分页。我们采用的标准化分页范例是，您可以结合使用 before 和 after ID 与 limit 来检索所需的结果页面。您需要参考具体的端点文档以获取详细信息。

    值得注意的是，雪花 ID 只是带有时间戳的数字，因此在处理分页时，如果您想要从时间开始（在 Discord 纪元中，但 0 也适用）或特定时间之前/之后的结果，您可以为该时间生成一个雪花 ID。

    从时间戳生成雪花 ID 示例
    (timestamp_ms - DISCORD_EPOCH) << 22

    ID 序列化

    在某些情况下，我们的 API 和网关可能会以意想不到的格式返回 ID。在内部，Discord 将 ID 存储为整数雪花。当我们把 ID 序列化为 JSON 时，我们会将 bigint 转换为字符串。鉴于所有 Discord ID 都是雪花，您应该始终期望得到一个字符串。

    然而，在某些情况下，向我们的 API 传递某些内容时，会返回序列化为整数的 ID；当您向我们的 API 或网关发送的 id 字段中的值不是 bigint 大小时，就会发生这种情况。例如，当从我们的网关请求 GUILD_MEMBERS_CHUNK 时：

    // 发送
{
op: 8 , 
d: {
　guild_id: '308994132968210433' , 
　user_ids: [ '123123' ]
}
}

// 接收
{
t: 'GUILD_MEMBERS_CHUNK' , 
s: 3 , 
op: 0 , 
d: {
　not_found: [ 123123 ] , 
　members: [] , 
　guild_id: '308994132968210433'
}
}

    您可以在此例中看到，发送的 user_id 不是 bigint；因此，当它被 Discord 序列化回 JSON 时，它没有被转换为字符串。这种情况绝不会发生在来自 Discord 的 ID 上。但是，如果您在请求中发送了格式错误的数据，就可能会发生这种情况。

    ISO8601 日期/时间

    Discord 对我们模型中返回的大多数日期/时间都采用了 ISO8601 格式。在本文档的表格中，这种格式被称为 ISO8601 类型。

    一致性

    Discord 的运行规模使得真正的一致性是不可能实现的。因此，我们的 API 和服务之间的许多操作都是最终一致的。

    由于这一点，客户端操作永远不能被序列化，并且可能以任何顺序执行（如果执行的话）。

    除了这些限制，Discord 中的事件可能：

    • 永远不会发送给客户端
    • 恰好发送给客户端一次
    • 最多发送给每个客户端 N 次

    客户端应尽可能以幂等行为处理来自 API 的事件和结果。

    HTTP API

    用户代理

    使用 HTTP API 的客户端必须提供有效的 User Agent，以以下格式指定客户端库和版本信息：

    用户代理示例
    User-Agent: DiscordBot ($url , $versionNumber)

    客户端可以根据需要在此字符串的末尾附加更多信息和元数据。

    未指定有效用户代理的客户端请求可能会被阻止，并返回 Cloudflare 错误。

    内容类型

    使用 HTTP API 的客户端必须提供有效的 Content-Type 标头，可以是 application/json、application/x-www-form-urlencoded 或 multipart/form-data，除非另有说明。未能这样做将导致 50035 “无效表单主体”错误。

    速率限制

    HTTP API 实施了一个根据 RFC 6585 限制和防止过度请求的过程。

    API 用户如果经常触及并忽视速率限制，其 API 密钥将被撤销，并被平台封禁。有关请求速率限制的更多信息，请参阅 速率限制 部分。

    布尔查询字符串

    API 中的某些端点被记录为接受布尔值作为其查询字符串参数。虽然查询字符串参数中没有布尔表示的标准系统，但 Discord 在这种情况下使用 True、true 或 1 表示真，使用 False、false 或 0 表示假。

    网关 (WebSocket) API

    Discord 的网关 API 用于在您的客户端和我们的服务器之间维护持久的、有状态的 WebSocket 连接。这些连接用于发送和接收您的客户端可以用来跟踪和更新本地状态的实时事件。网关 API 使用 RFC 6455 中指定的安全 WebSocket 连接。

    有关打开网关连接的信息，请参阅 网关 API 部分。

    签名附件CDN URL

    上传到Discord CDN的附件（例如用户和机器人上传的图片）具有带有预设过期时间的签名URL。Discord会自动刷新客户端中显示的附件CDN URL，因此当您的应用收到包含签名URL的有效负载（例如当您获取消息时），它将是有效的。

    当将CDN URL传递到API字段时，例如嵌入图片对象中的url和用于webhook的avatar_url，您的应用可以将CDN URL作为值直接传递，无需任何参数，Discord将自动渲染和刷新该URL。

    上传文件

    文件上传大小限制适用于请求中的每个文件。所有用户的默认限制为 10 MiB，但根据用户的 Nitro 状态或服务器的 Boost Tier 可能会更高。

    在 处理交互时 提供的 attachment_size_limit 值是这些值中的最大值。

    一些端点支持文件附件，通过 files[n] 参数指示。要添加文件，标准的 application/json 请求体必须替换为 multipart/form-data 请求体。JSON 消息体可以使用 payload_json 参数选择性地提供。

    所有 files[n] 参数都必须包含一个有效的 Content-Disposition 子部分头部，其中包含 filename 和唯一的 name 参数。每个文件参数都必须以 files[n] 的格式唯一命名，例如 files[0]、files[1] 或 files[42]。

    带有后缀的索引 n 是雪花占位符，可用于 attachments 字段，该字段可传递给 payload_json 参数（或 回调数据负载）。

    attachments JSON 参数包含将附加到消息的所有文件，包括新文件及其各自的雪花占位符（如上所述）。

    当发出 PATCH 请求时，只有 attachments 参数中列出的文件才会被附加到消息中。任何以前添加但未包含的文件将被移除。

    示例请求体 (multipart/form-data)

    请注意，这些示例是 HTTP 请求的小部分，用于演示此端点的行为——客户端库将设置自己的表单边界（boundary 只是一个示例）。

    更多信息请参阅 multipart/form-data 规范。

    此示例演示了不使用 payload_json 的端点用法。

    --boundary
Content-Disposition: form-data ; name="content"

Hello , World ! 
--boundary
Content-Disposition: form-data ; name="tts"

true
--boundary--

    此示例演示了使用 payload_json 并设置所有内容字段（content、embeds、files[n]）的端点用法。

    --boundary
Content-Disposition: form-data; name="payload_json"
Content-Type: application/json

{
  "content": "Hello, World!",
  "embeds": [{
    "title": "Hello, Embed!",
    "description": "This is an embedded message.",
    "thumbnail": {
      "url": "attachment://myfilename.png"
    },
    "image": {
      "url": "attachment://mygif.gif"
    }
  }],
  "message_reference": {
    "message_id": "233648473390448641"
  },
  "attachments": [{
      "id": 0,
      "description": "Image of a cute little cat",
      "filename": "myfilename.png"
  }, {
      "id": 1,
      "description": "Rickroll gif",
      "filename": "mygif.gif"
  }]
}
--boundary
Content-Disposition: form-data; name="files[0]"; filename="myfilename.png"
Content-Type: image/png

[image bytes]
--boundary
Content-Disposition: form-data; name="files[1]"; filename="mygif.gif"
Content-Type: image/gif

[image bytes]
--boundary--
    在嵌入中使用附件

    您可以在创建消息时上传附件，并在嵌入中使用这些附件。为此，您需要将文件作为 multipart/form-data 请求体的一部分上传。请确保您上传的文件包含文件名，因为您需要在负载中引用它。

    目前只允许使用.jpg、.jpeg、.png、.webp和.gif文件。其他文件类型不受支持。

    在一个嵌入对象中，你可以使用附件方案语法将图像的URL设置为一个附件：attachment://filename.png

    例如：

    {
  "embeds": [{
    "image": {
      "url": "attachment://screenshot.png"
    }
  }]
}
